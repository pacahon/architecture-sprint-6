### Проблемы и риски

* Синхронное взаимодействие с внешними сервисами при получении данных о доступных продуктах может приводить не только к задержкам, но и падению операции в целом. Чем больше внешних сервисов, тем выше время ответа и вероятность сбоя.
Из-за этого изменения тарифов и данных о продуктам могут появляться с задержкой, а документ для взаиморасчетов и вовсе может быть не сформирован.
* Нарушение согласованности данных между сервисами, т.к. они синхронизируют данные с разной частотой:
    * core-app -> ins-product-aggregator раз в 15 минут
    * ins-comp-settlement -> ins-product-aggregator раз в сутки
* core-app является монолитом, которым пользуются как клиенты, так и партнёры, т.е. это единая точка входа и отказа, которая не может гибко масштабируется. Например, при росте кол-ва товаров придется масштабировать весь остальной функционал.
* При отправке отчетов в сторонние системы используются синхронные операции, которые могут упасть и отчет не будет доставлен.
* Сервис взаиморасчетов может нагрузить core-app в моменте ночью, тем самым влияя на функционал по оформлению страховок.

### Решение

* Асинхронно получаем данные по продуктам и тарифам из внешних систем и складываем их в локальную БД рядом с ins-product-aggregator, она же станет мастер-системой для них:
    * Уберём рассинхрон данных между core-app и ins-comp-settlement по продуктам и тарифам
    * Возможно, с некоторыми внешними системами получится интегрироваться через прослушивание событий и доставлять данные в околореальном времени.
    * Можно организовать синхронизацию только измененных данных, а не делать полный снэпшот данных внешней системы.
    * Если часть данных по товарам и продуктам всё равно нужно держать в core-app и ins-comp-settlement, то можно публиковать события с этими данными в брокер сообщений.
* ins-comp-settlement перевести на асинхронное взаимодействие с core-app и начать слушать события об оформленных заявках
* При отправке отчетов во внешние системы используем transactional outbox, чтобы сформированные отчеты гарантировано были доставлены, как только внешняя система готова его принять – запускаем задачу на отправку по крону каждый час.
